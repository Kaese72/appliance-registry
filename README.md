# Appliance registry

This service keeps track of appliances.

## Background

Today a Huemie appliance (one physical/local Kubernetes cluster running
`device-store`, `adapter-attendant`, `ittt-orchestrator`, etc.) is entirely
self-contained. Nothing about the core system requires the cloud. Cloud
connectivity is provided separately by [cloud-connect](../cloud-connect),
which today is wired up by hand: a single hostname baked into the cloud
ingress, and a shared secret created manually with `kubectl create secret`
in both the cloud and appliance clusters (see cloud-connect's README).

That works for a single, permanently-known appliance. It does not work once
there is more than one appliance (a second home, a friend's install, ...):
there needs to be somewhere that knows an appliance exists, which cloud
hostname belongs to it, who owns it, and how to hand it the credentials it
needs to stand up its tunnel — without a human hand-typing secrets into two
clusters every time.

That's what this service is for. It does not implement the tunnel itself
(that's still cloud-connect) or authenticate end users (that's
[authentication](../authentication) and
[cloud-user-registry](../cloud-user-registry)) — it is the source of truth
for "which appliances exist" and the mechanism by which an appliance goes
from freshly installed to holding the secrets it needs to talk to the cloud.

**Registering with this service is optional.** An appliance that never
registers keeps working exactly as it does today, purely locally, with no
cloud connectivity at all. Registration is only how an owner opts an
appliance into cloud-connect (remote access) and, in the future, other
appliance-scoped cloud functionality.

## Models

### Appliance

An **Appliance** represents one physical/local Huemie install.

* A name (human-friendly, chosen by the owner)
* A hostname (the `*.appliance.humi.kaese.space` subdomain the appliance is
  reachable at through cloud-connect once claimed)
* An owning **Group** (from cloud-user-registry — whoever administers that
  Group administers the appliance)
* A status: `pending` (created, not yet claimed), `active` (claimed and in
  use), `revoked` (access withdrawn, credentials no longer valid)
* Timestamps: created, last claimed, last seen

### Claim token

A **Claim token** is a single-use secret generated alongside a `pending`
**Appliance**. It exists only to bootstrap trust with an appliance that
doesn't have any cloud credentials yet — see "Claiming" below. It is scoped
to exactly the one **Appliance** it was issued for (checked against the
`{id}` in the claim URL — a valid token for appliance A does not claim
appliance B), and consumed (deleted/invalidated) the first time it's
successfully used. It also carries its own short expiry so an un-claimed
appliance doesn't sit around indefinitely as a valid credential.

### Appliance secret

The **Appliance secret** is the cloud-connect shared secret (the `auth`
value cloud-connect's chisel client/server use — see cloud-connect's
README) generated by this service for a given **Appliance**. This service
is the only thing that generates it; cloud-connect just consumes it.

## Functionality

### Registration

An *administrator* of a **Group** (authenticated the same way as
cloud-user-registry — a `use` JWT carrying the group id) can register a new
**Appliance** by providing a name. This:

1. Creates the **Appliance** in `pending` status, owned by that Group.
2. Allocates it a hostname.
3. Generates a **Claim token** and returns it in the response, once. It is
   not retrievable again — if it's lost before the appliance is claimed,
   the registration has to be discarded and redone.

This step happens from the cloud UI, before the appliance's local cluster
is ever touched.

### Claiming

The freshly-installed appliance is the one thing that doesn't yet have any
cloud identity, so it authenticates with the **Claim token** instead of a
user JWT. During initial setup of the appliance cluster (installer/CLI
step, not part of the normal gitops sync), the operator supplies the
appliance id and claim token they were given during registration. The
appliance calls this service once:

```
POST /appliance-registry/v0/appliances/{id}/claim
Authorization: Bearer <claim token>
```

and receives back:

* The generated **Appliance secret** (the cloud-connect `auth` value)
* The assigned hostname
* The chisel server URL to tunnel to (`wss://<hostname>/cloud-connect/v0/tunnel`)

The claim token is invalidated immediately after a successful claim (or on
expiry, whichever comes first), and the **Appliance** moves to `active`.
This service only ever writes the generated secret into its own (cloud)
cluster, as `cloud-connect-secret-<id>` — see "Cloud-side
cloud-connect-server provisioning" below. It has no access to the
appliance's own cluster, so the response body (secret, hostname, tunnel URL)
is the only place the appliance side ever sees the secret; something on the
appliance itself is responsible for persisting it locally. Historically that
was a manual operator step (`kubectl create secret` on the appliance
cluster, using the values from this response) — see "Enrollment" below for
the flow that replaces that manual step.

A claim can only succeed once. A lost/expired claim token, or an appliance
stuck in `pending` for too long, is handled by an administrator re-issuing
a new claim token for the same **Appliance** (invalidating any prior one)
rather than by the appliance retrying indefinitely.

### Enrollment

**Enrollment** is the human-friendly, redirect-driven alternative to
Registration + Claiming above, used by `cloud-connect-client`'s "Connect to
Cloud" flow (see cloud-connect's README). It reuses the same underlying
state machine — a `pending` **Appliance** plus a **Claim token** — but never
exposes the claim token to a browser:

```
POST /appliance-registry/v0/appliances/enroll
Authorization: Bearer <use token>
```

Called from the cloud UI once the user is authenticated. It registers a new
**Appliance** exactly like Registration, but instead of returning the raw
claim token, it wraps it in a short-lived, single-use **exchange code** and
returns `{applianceId, exchangeCode, exchangeCodeExpiresAt}`. The browser is
then redirected back to the appliance's own local UI with that code (and the
appliance id) in the URL — the appliance never trusted with more than that.

The appliance's own `cloud-connect-client` redeems the code itself,
server-to-server, independent of the tunnel (which doesn't exist yet):

```
POST /appliance-registry/v0/appliances/{id}/enroll/redeem
Authorization: Bearer <exchange code>
```

This performs the same state transition as Claiming (generate the
**Appliance secret**, write the cloud-side Secret, mark the **Appliance**
`active`) and returns the same response shape Claiming does. The exchange
code is checked against the claim token that was live when it was issued, so
it can't be redeemed after that claim token has been superseded (e.g. a
second enrollment attempt for the same appliance) — and, like a claim token,
it is single-use and short-lived.

### Cloud-side cloud-connect-server provisioning

Claiming an appliance also has to stand up its cloud-side half of the
tunnel: a dedicated `cloud-connect-server-<id>` Deployment, Service,
Ingress (on the appliance's hostname) and NetworkPolicy in the
`huemie-cloud` namespace — one per **Appliance**, reusing the existing
single-tenant `cloud-connect-server` image/manifest as-is (see
cloud-connect's README) rather than making that server multi-tenant.

This is split across two mechanisms, so that secret material never has to
be committed to `huemie-gitops-base`:

* **The Deployment/Service/Ingress/NetworkPolicy** (no secret values, just
  the appliance id and hostname) are generated by an ArgoCD
  `ApplicationSet` using a
  [Plugin generator](https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-Plugin/),
  templating one child `Application` per active appliance, the same way
  `application-crds/` in hallen-gitops-base templates one Application per
  operator/instance. This service speaks that generator's wire protocol
  directly, at `POST /appliance-registry/v0/argocd-plugin/api/v1/getparams.execute`
  (ArgoCD's fixed suffix on whatever `baseUrl` the plugin is registered
  with), rather than a separate plugin service being stood up — it's just
  another route on this service, backed by the same active-appliances
  query as `GET /appliance-registry/v0/appliances?status=active`. Only
  `active` appliances are ever returned, so nothing gets deployed before
  its secret exists. See huemie-gitops-base's
  `cloud/application-crds/applicationset-cloud-connect-server-fleet.yaml`
  for the ApplicationSet itself and the per-instance Kustomize base it
  templates. This is neither a user (no JWT) nor an appliance (no claim
  token) calling — the plugin registration carries its own static bearer
  token (ArgoCD's plugin-generator convention: a `Secret` in the `argocd`
  namespace holding it, referenced by a `ConfigMap` that names this
  service's `baseUrl`), checked here as a distinct auth path from the JWT
  and claim-token ones above, since the caller has neither a group id nor
  an appliance id to present. Without it the endpoint would leak every
  appliance's id/hostname to an unauthenticated caller and let anyone
  force reconciliation.
* **The `cloud-connect-secret-<id>` Secret** those manifests reference is
  *not* templated by the ApplicationSet — it's written directly into the
  `huemie-cloud` namespace by this service at claim (and rotate) time,
  using the same idempotent-in-cluster-write pattern already used for
  `jwt-secret`/the MariaDB root password elsewhere in this codebase,
  instead of a fresh mechanism. This service holds a Kubernetes
  ServiceAccount scoped to create/update `Secret` objects (only, in that
  one namespace) for exactly this purpose.

If an appliance is later revoked, its ApplicationSet-generated Application
is pruned (the entry drops out of the `status=active` list) and its Secret
is deleted the same way it was created.

### Revocation / rotation

Every one of these calls checks that the JWT's group id matches the
**Appliance**'s `owning_group_id` — being *an* administrator isn't enough,
it has to be an administrator of *that appliance's* Group, same as
cloud-user-registry's rule that only admins of a Group can act on
resources that Group owns. A mismatch is a 404, not a 403, so the endpoint
doesn't leak the existence of appliances owned by other Groups.

An *administrator* of the owning **Group** can:

* **Revoke** an **Appliance** — status moves to `revoked`, its
  **Appliance secret** stops being valid (cloud-connect-server refuses the
  tunnel), and its hostname is freed. Does not touch the appliance's local
  cluster; the appliance simply loses cloud connectivity until re-claimed.
* **Rotate** an **Appliance secret** — generates a new secret without
  changing the hostname or status. Used if a secret is suspected
  compromised. The appliance needs to be updated with the new secret
  out-of-band (re-running the claim-equivalent step, or a future
  authenticated "refresh" endpoint — not yet implemented).

### Listing

A *administrator* of a **Group** can list the **Appliances** owned by that
Group (only that Group's — the JWT's group id scopes the query, same
authorization rule as above), along with status and last-seen, for a
simple "is my appliance online" view in the cloud UI.

Revoked appliances are omitted by default; pass `?includeRevoked=true` to
include them. `?status=` narrows to a single status (so `?status=revoked`
returns revoked appliances without needing `includeRevoked`). Both filters
are applied in the database query.

## Architecture

* Data stored in MariaDB, same pattern as cloud-user-registry.
* REST API under `/appliance-registry/v0/...`.
* Three distinct caller types, three distinct auth mechanisms — nothing is
  left unauthenticated:
  * **A logged-in user** (register/list/revoke/rotate) — a `use` JWT
    issued by cloud-user-registry, carrying the user and group id. It is
    verified against cloud-user-registry's public key using that service's
    public `cloudtoken` package (`cloudtoken.FromAuthHeader`), so the token
    format is defined in one place rather than re-implemented here. Every call is further authorized against that group id
    matching the target **Appliance**'s owning Group (see "Revocation /
    rotation" above) — the JWT alone proves *who*, not *allowed to touch
    this appliance*.
  * **A freshly-installed appliance** (claim only) — the claim token,
    scoped to one appliance id, single-use (see "Claim token" above). It
    has no JWT because it has no user/group identity at that point.
  * **The ArgoCD ApplicationSet Plugin generator** (the active-appliances
    list only) — a static service bearer token, distinct from both of the
    above, since this caller has neither a group id nor an appliance id to
    present (see "Cloud-side cloud-connect-server provisioning" above).
* This service does not talk to an appliance's local cluster directly, and
  an appliance never receives cloud-admin credentials. It only ever pulls
  cloud-connect credentials for itself, once, via the claim flow.
* This service does have a narrow write path into the cloud cluster: a
  ServiceAccount limited to creating/updating/deleting `Secret` objects in
  the `huemie-cloud` namespace, used only to publish/rotate/remove
  `cloud-connect-secret-<id>` for cloud-side `cloud-connect-server-<id>`
  pods (see "Cloud-side cloud-connect-server provisioning" above). It has
  no other Kubernetes permissions.
* `GET /appliance-registry/v0/appliances?status=active` is a second,
  narrower-purpose read endpoint (no secret material, just id/hostname)
  meant to be polled by the ArgoCD ApplicationSet Plugin generator that
  provisions cloud-side `cloud-connect-server-<id>` resources — see above.

## Future / explicitly out of scope for now

The Appliance record is intended to become the anchor point other
appliance-scoped cloud functionality hangs off later (e.g. a multi-appliance
dashboard, remote diagnostics, version/health reporting). None of that is
part of this service yet — today it only exists to make cloud-connect
onboarding for a new appliance a registration + claim instead of manual
`kubectl` steps in two clusters, and everything above should be read with
that narrow scope in mind.
